# ESP32 Linear Actuator Controller

PlatformIO/Arduino firmware for independently testing two STEP/DIR/ENABLE
stepper axes from a responsive web interface. Motion is generated by
FastAccelStepper using the ESP32 MCPWM/PCNT peripherals, so Wi-Fi requests do
not determine pulse timing.

This repository has two deliberate roles:

1. `src/main.ino` is the working hardware bring-up and diagnostic firmware. It
   verifies wiring, directions, limits, speeds, and mechanics without pretending
   to be a CNC controller.
2. `fluidnc/config.yaml` is the validated migration configuration for FluidNC,
   which will provide proper homing, coordinated X/Y interpolation, machine and
   work coordinates, and G-code file execution.

## Current project state and handoff

As of 2026-09-14, the two-axis diagnostic firmware has been built, flashed, and
tested on the physical machine. Both axes move reliably, both limit inputs have
been electrically and mechanically verified, negative coordinate motion has
been calibrated to travel toward the minimum/home switches, and a supervised
two-pass homing sequence has succeeded on both axes.

The A4988 MS1/MS2/MS3 DIP switches are now all ON for 1/16 microstepping. Each
axis uses a 1.8-degree, 200-step/revolution NEMA-17, a GT2 belt, and a 20-tooth
pulley. Therefore:

```text
200 full steps/rev * 16 microsteps / (20 teeth * 2 mm) = 80 steps/mm
1 microstep = 0.0125 mm commanded resolution
```

Measured physical travel is 96.5 mm on X and approximately 100 mm on Y. The
FluidNC file intentionally uses smaller 95 mm and 98 mm software travels to keep
margin away from the positive mechanical ends.

FluidNC **has not been flashed yet**. The official FluidNC v4.0.3 Windows bundle
and current official validator were downloaded locally under ignored `.tools/`.
`fluidnc/config.yaml` passes the official strict validator. The next operator
must turn off the 12-24 V motor supply before replacing firmware; see
"FluidNC commissioning" below.

## Hardware

| Signal | ESP32 pin | Notes |
| --- | ---: | --- |
| X STEP | GPIO 25 | MCPWM-generated pulse output |
| X DIR | GPIO 26 | Positive/negative X direction |
| X ENABLE | GPIO 27 | Active LOW; enabled after safe initialization |
| Y STEP | GPIO 16 | MCPWM-generated pulse output |
| Y DIR | GPIO 17 | Positive/negative Y direction |
| Y ENABLE | GPIO 22 | Active LOW; enabled after safe initialization |
| X minimum/home switch | GPIO 32 | NO contact to GND; internal pull-up |
| Y minimum/home switch | GPIO 13 | NO contact to GND; internal pull-up |

Connect ESP32 ground to the stepper driver's logic/power ground. Never connect
or disconnect motor coils while the driver is powered. Set the driver's current
limit for the connected motor before extended operation.

Each normally-open limit switch connects only its assigned GPIO to GND when
pressed. The internal pull-up makes an unpressed switch read HIGH and a pressed
switch read LOW, so no external resistor is required. The manual API blocks
negative motion while its minimum switch is pressed, but permits positive
motion so the operator can back away. NO wiring is minimal but not fail-safe: a
broken wire looks like an unpressed switch. GPIO 18/19/23/5 are deliberately
reserved for a future VSPI SD card.

Both direction-pin mappings were bench-calibrated so negative coordinate motion
travels toward the corresponding minimum/home switch. Revalidate this behavior
if any motor leads, driver connections, or mechanical transmission change.

### Motion hardware

- Two A4988 StepStick drivers, configured by carrier-board DIP switches
- MS1, MS2, and MS3 all ON: 1/16 microstepping
- Two 1.8-degree NEMA-17 motors (200 full steps/revolution)
- GT2 2 mm-pitch belts with 20-tooth pulleys
- X calibration: 80 steps/mm; measured travel: 96.5 mm
- Y calibration: 80 steps/mm; measured travel: approximately 100 mm

## Build and configuration

1. Install PlatformIO.
2. Copy `src/secrets.example.h` to `src/secrets.h`.
3. Set the 2.4 GHz station credentials and direct access-point credentials.
4. Run `pio run` to build.
5. Run `pio run --target upload --upload-port COM4` (adjust the port as needed).
6. Use a 115200-baud serial monitor to read assigned IP addresses.

`src/secrets.h` is intentionally ignored by Git. If it is absent, the example
placeholder values are used so a clean checkout can still compile.

The only external Arduino library is pinned in `platformio.ini`:

- FastAccelStepper 0.31.8

## Network behavior

The ESP32 starts in AP+station mode:

- It selects the strongest matching 2.4 GHz access point and retains the
  strongest WPA2-only radio as a compatibility fallback.
- It also exposes the configured direct AP, normally reachable at
  `http://192.168.4.1`.
- Station failure does not prevent the direct AP or web server from operating.

Wi-Fi station power saving is disabled to reduce interactive latency. The web
page also permits only one status request at a time, preventing slow polls from
accumulating ahead of motion commands on the synchronous ESP32 WebServer.

## HTTP API

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/` | Embedded mobile control page |
| GET | `/status` | Nested X/Y position, motion, settings, and limit state |
| POST | `/move` | Relative move; `axis=x|y`, `direction=positive|negative` |
| POST | `/stop` | Controlled stop; `axis=x|y|all` |
| POST | `/zero` | Zero selected `axis=x|y` while stopped |
| POST | `/settings` | Apply settings to selected `axis=x|y` |

## Motion and position semantics

FastAccelStepper queues motion and produces pulses independently of Arduino's
`loop()`. `loop()` only services the synchronous web server. Position remains
open-loop: PCNT counts generated STEP pulses, but there is no encoder confirming
that the motor physically moved. STOP decelerates normally rather than removing
torque abruptly.

The future `homeStepper()` placeholder describes the intended switch sequence.
Implement it as a non-blocking state machine so web requests and STOP remain
responsive.

### Known diagnostic-firmware limitations

- `homeStepper()` is intentionally a documented placeholder; there is no
  automatic `/home` endpoint. The successful calibration homing was supervised
  using bounded API moves: seek, interrupt stop, 3 mm pull-off, slow approach,
  and `setCurrentPosition(0)`.
- Limit switches are normally open to minimize component count. A broken wire
  therefore looks like a safe, released switch. Normally-closed switches and a
  physical emergency stop are recommended before unattended machine use.
- The diagnostic ISR force-stops an axis on every falling limit edge, regardless
  of movement direction. Mechanical contact bounce can interrupt a move away
  from the switch; this was observed during pull-off and handled with a second
  bounded move. FluidNC replaces this temporary behavior with its homing logic.
- X and Y are independently commanded. This firmware does not calculate a
  coordinated line, arc, junction velocity, or tool path.
- Position is commanded open-loop position and resets when firmware restarts.
  There are no motor encoders.
- The drivers remain enabled after safe initialization to preserve holding
  position. A4988 current limits must be adjusted correctly, and driver/motor
  temperature must be monitored.
- There is currently no dedicated hardware emergency-stop input.

## Planned CNC/G-code transition

This custom firmware is intentionally a two-axis electrical and mechanical
bring-up tool; it does not coordinate axes or interpret G-code. Once both axes,
directions, steps-per-distance, and limit switches are validated, migrate the
same pin map to FluidNC. FluidNC provides coordinated interpolation, machine and
work coordinates, homing cycles, hard/soft limits, WebUI control, and execution
of uploaded or SD-card G-code without maintaining a custom motion planner.

The validated migration configuration is in `fluidnc/config.yaml`. It records
the A4988 1/16 microstep setting, 20-tooth GT2 calibration (80 steps/mm),
calibrated direction polarity, conservative travel limits, and sequential X/Y
homing. Keep this diagnostic firmware available until FluidNC commissioning is
complete; flashing FluidNC replaces the application currently on the ESP32.

## FluidNC commissioning

Use official FluidNC v4.0.3 or a later version only after reviewing its release
notes and revalidating the YAML against that version. The present configuration
uses:

- ESP32 RMT hardware stepping
- Cartesian X/Y kinematics
- 80 steps/mm on both axes
- 750 mm/min initial maximum rate
- 10 mm/s^2 initial acceleration
- X then Y sequential two-pass homing
- 300 mm/min seek, 60 mm/min precision approach, and 3 mm pull-off
- Active-low inputs with internal pull-ups (`gpio.32:low:pu` and
  `gpio.13:low:pu`)
- A4988 active-high disable semantics on GPIO 27 and GPIO 22
- Hard limits, soft limits, and mandatory homing after restart

Commission in this order:

1. Preserve this repository and confirm `fluidnc/config.yaml` validates.
2. Move both carriages off their switches; the last diagnostic session moved
   both 3 mm positive and confirmed both inputs released.
3. Turn off the 12-24 V motor supply. Leave only ESP32 USB connected.
4. Erase the ESP32, install the official FluidNC Wi-Fi firmware and WebUI
   filesystem, then upload `fluidnc/config.yaml` as `/config.yaml`.
5. Inspect the complete serial startup report. Do not apply motor power if any
   pin, parser, filesystem, or configuration error appears.
6. With motor power still off, verify limit states and ENABLE/DIR/STEP polarity.
7. Apply motor power, test small positive jogs, and confirm each axis moves away
   from its negative switch.
8. Run `$H` while supervising the machine and keeping power removal within
   reach. Confirm X homes first, followed by Y, and both pull off cleanly.
9. Verify millimeter motion using a small `G91 G0 X10` / `G0 Y10` test and
   measure actual travel before enabling unattended jobs.
10. Dry-run a small G-code file with the mechanism unloaded before running a
    real process.

The standard VSPI pins GPIO 18/19/23/5 remain unused, allowing a later SD-card
interface. FluidNC can initially upload and run small G-code files from its
local flash filesystem, so an SD-card module is not required for first tests.
